# papi

Базовый проект админ-панелей. Это не библиотека, а готовая, запускаемая панель, у которой
ядро вынесено в отдельную папку.

```
lib/    ядро — общий каркас, тема, стор, api, i18n. В панелях read-only
src/    панель — её страницы, слайсы, эндпоинты, словари
```

Панель создаётся клоном этого репозитория и обновляет ядро обычным `git merge`. Отдельной
npm-зависимости нет: Vite компилирует `lib/` вместе с `src/`, поэтому правка ядра видна тем
же HMR, что и правка панели, — шага сборки между ними нет.

В `src/` лежит не пустой скелет, а работающая эталонная панель: список пользователей с
созданием и удалением, страница настроек, свой слайс и свои эндпоинты. Она показывает, как
пользоваться ядром, и заменяется на страницы своей панели после форка.

Бэкенда к ней в репозитории нет — запросы уходят по адресу из `VITE_API_BASE_URL`. Чтобы
увидеть панель с данными, нужен либо настоящий бэкенд, либо локальный мок; в репозиторий мок
не попадает намеренно — у каждой панели он свой.

## Создать панель

```bash
git clone <papi-url> my-panel && cd my-panel
npm run setup
npm run dev
```

`npm run setup` — это `scripts/setup-panel.mjs`. Он спрашивает имя панели, аббревиатуру, имя
пакета, префикс эндпоинтов и адрес своего репозитория (последнее необязательно), показывает,
что собирается сделать, и делает: переименовывает `origin` в `upstream`, ставит свой `origin`,
правит `name` в `package.json`, собирает `.env` из образца, зовёт `npm install` и коммитит
получившееся. Push спрашивается отдельно и последним.

Ответ по умолчанию стоит в строке ввода серым: Enter принимает его как есть, Tab вписывает
его настоящим текстом — чтобы поправить, — а любая буква начинает свой ответ. Адрес
репозитория панели скрипт собирает из адреса ядра, меняя в нём одно имя; если своего
репозитория пока нет, этот вопрос пропускается ответом `-`.

Ctrl+C выходит, ничего не тронув, `--help` показывает справку, а ответы можно подать и файлом:
`node scripts/setup-panel.mjs < answers.txt`, по строке на вопрос. Серых заготовок там нет —
подсказка печатается словами в скобках.

Запускается до установки, потому что зависимостей у него нет — только встроенные модули node, а
`npm run` содержимого `node_modules` не требует. Второй раз он не пройдёт: имя пакета уже не
`papi`, значит клон настроен.

Дальше остаётся своё: страницы в `src/` и запись панели в каталоге логотипов — но она в ядре,
то есть в репозитории papi (см. `PanelLogo` ниже).

То же руками, если скрипт чем-то не подошёл:

```bash
git clone <papi-url> my-panel && cd my-panel
git remote rename origin upstream
git remote add origin <my-panel-url>
git push -u origin main
npm install
cp .env.example .env
npm run dev
```

Плюс `name` в `package.json` и имя с аббревиатурой в `.env`. Иконку в `index.html` менять не
нужно — она собирается из аббревиатуры.

Переименовать `name` стоит сразу и по второй причине: по нему хук отличает панель от самого
papi в тех клонах, где ремоута `upstream` нет, — а его нет у всех, кроме того, в котором форк
делали руками. На витрину `name` не выходит — это слаг пакета, а не имя панели.

Имя панели задаётся в `.env` один раз и расходится само:

```bash
VITE_APP_NAME=Really Mighty Panel
VITE_APP_ABBR=RMP
```

`VITE_APP_NAME` уходит во вкладку браузера: `<title>` в `index.html` содержит `%VITE_APP_NAME%`,
его подставляет Vite. В коде оба значения доступны через `getAppName()` и `getAppAbbr()` из
`@papi/services`; `VITE_APP_ABBR` без неё берётся из первых букв слов имени.

На них же строится `LogoTemplate` из `@papi/components` — красная пилюля с иконкой панели,
буквами аббревиатуры и именем второй строкой. Размера три: `large` — всё вместе, `middle` — иконка и
буквы, `small` — круг с одной иконкой. Иконка передаётся элементом, цвет заливки — пропом
`color`, по умолчанию это красный из логотипа ядра (`PAPI_LOGO_COLOR`):

```tsx
<LogoTemplate size="middle" abbr="RMP" name="Risk Management Panel" icon={<TriangleAlert />} />
```

Панели, которые уже собраны на papi, перечислены в каталоге `panelLogos` рядом с компонентом
`PanelLogo` — он подставляет запись по короткому имени панели, чтобы места вызова не таскали за
собой брендовые строки:

```tsx
<PanelLogo size="middle" />
```

Своя панель тут не называется вовсе: короткое имя берётся из `VITE_APP_ABBR` (`RMP` — запись
`rmp`), поэтому вызов один и тот же во всех клонах. Проп `panel` остаётся для чужого логотипа —
витрина, список панелей: `<PanelLogo panel="rmp" />`.

Каталог в ядре, потому что имя, аббревиатура и иконка — ровно то, чем панели отличаются друг от
друга; собранные в одном месте, они не расходятся между клонами. Новая панель дописывается в
`lib/components/shared/PanelLogo.tsx` и приезжает к остальным обычным merge. Рядом с
компонентом, а не в `constants/`, — потому что иконка это разметка, и в `.ts` её не написать.

Панели, которой в каталоге ещё нет, и `LogoTemplate`, и `PanelLogo` подставят имя с аббревиатурой
из `.env` — та же пилюля, только без иконки.

Тот же знак стоит и во вкладке браузера. Иконку на круг ставит `PanelFavicon` — его рендерит
`PapiProvider`, настраивать ничего не нужно. До загрузки скриптов во вкладке видны буквы:
их рисует `index.html`, подставляя туда `VITE_APP_ABBR`, — поэтому для иконки вкладки переменную
задают явно, из имени она там не соберётся.

## Обновить ядро

```bash
git fetch upstream
git merge upstream/main
```

Merge, а не rebase: у панели своя история, переписывать её нельзя.

Всё, что приезжает в `lib/`, встаёт без конфликтов — панель этих файлов не касалась.
Конфликт возможен там, где панель правила общие файлы: корневые конфиги и `package.json`.
Разрешается вручную, по обычным правилам merge.

Отдельный случай — `src/`. Обычно ядро его не трогает, но в самом papi там лежит скелет
панели, и при ломающем изменении контракта он меняется вместе с ядром. Тогда конфликт
приходит в файлы, которые панель считает своими, — что с ним делать, написано ниже.

## Ломающие изменения ядра

То, что не встаёт мержем само и требует правки на стороне панели. Новое дописывается сверху.

### Имя панели берётся из `.env`

`<title>` в `index.html` стал `%VITE_APP_NAME%`, и ядро читает имя через `getAppName()`. Панели
нужно дописать в `.env` переменную (образец — в `.env.example`):

```bash
VITE_APP_NAME=Really Mighty Panel
```

Без неё вкладка покажет буквальное `%VITE_APP_NAME%` — Vite неизвестные переменные не заменяет,
— а `getAppName()` вернёт `papi` с предупреждением в консоли. Строку в своём `index.html`
панель заменяет на плейсхолдер сама, иначе имя будет жить в двух местах.

### `PAPI_ROUTES` переехал в `@papi/constants` и стал `papiRoutes`

Адреса ядра лежали в `lib/routing`, рядом с роутером. Теперь они в `lib/constants`, со всеми
остальными константами ядра, и называются как все остальные экспорты ядра — `papiRoutes`:

```ts
// src/constants/routes.constants.ts
-import { PAPI_ROUTES } from '@papi/routing';
+import { papiRoutes } from '@papi/constants';

 export const ROUTES = {
-  ...PAPI_ROUTES,
+  ...papiRoutes,
   users: '/users',
 } as const;
```

Тем же переездом `PapiLoginState` — то, что гард кладёт в `state`, уводя на вход, — ушёл в
`@papi/types`: это тип, и среди констант ему было не место. Панели он нужен, только если она
рисует свою страницу входа через `loginElement` и читает из `state` адрес, с которого увели.

Заодно `rtkTags` ядра стал `papiRtkTags`. Панель его не импортирует: свой набор она получает от
`injectTags`, и теги ядра лежат в нём же — см. раздел ниже.

### Теги объявляются один раз, а не в каждом файле эндпоинтов

`createApi` в ядре больше не идёт с пустым `tagTypes`: туда сразу уходит весь `papiRtkTags`.
Файлам эндпоинтов ядра `enhanceEndpoints` поэтому не нужен — они начинают с
`injectEndpoints`.

Панель делает то же самое одной строкой — `injectTags` из `@papi/api`. Он дописывает её теги в
набор api ядра и возвращает **весь** набор, вместе с тегами ядра:

```ts
// src/constants/tags.constants.ts
import { injectTags } from '@papi/api';

export const rtkTags = injectTags({
  user: 'User',
  order: 'Order',
});
```

`as const` тут не нужен: литералы `injectTags` забирает сам.

Занятое ядром он не пускает — ни ключ, ни само значение тега, — и пропущенное пишет
предупреждением в консоль. Пропущенного нет и в типе: `rtkTags.profile` после
`injectTags({ profile: 'Me' })` не соберётся. Иначе панель получила бы тег, который выглядит
своим, а сбрасывает кеш ядра.

Типы приезжают отдельным объявлением — тем же приёмом, что права и ключи каталога:

```ts
// src/types/tags.d.ts
import type { rtkTags } from '../constants/tags.constants';

declare global {
  namespace Papi {
    interface ApiTags {
      values: (typeof rtkTags)[keyof typeof rtkTags];
    }
  }
}
```

Дальше каждый `<имя>.api.ts` берёт `api` из `@papi/api` и сразу зовёт `injectEndpoints`.
Второго api у панели больше нет: `injectTags` меняет набор тегов у существующего, поэтому
`appApi` и `enhanceEndpoints` не нужны — и вместе с ними исчезает ошибка «взял `api` вместо
`appApi`, и свой же тег не проходит по типам». Тег ядра (`rtkTags.me`) лежит в том же объекте,
импортировать его из `@papi/constants` не нужно.

Что сделать в панели: перечислить свои теги в `src/constants/tags.constants` через `injectTags`,
завести `src/types/tags.d.ts`, убрать `enhanceEndpoints` из файлов эндпоинтов и заменить в них
`appApi` на `api`. Без `src/types/tags.d.ts` сборка не сломается: тип тега схлопнется в `string`,
и `providesTags` просто перестанет их проверять.

### Раздел закрывается правом

У `PapiRoute` появилось необязательное `permission`. Есть оно у раздела — раздел исчезает из
меню и отвечает `ForbiddenPage` по прямому адресу, пока у вошедшего нет этого права. Нет —
раздел открыт всем вошедшим, как и раньше.

Права ядро берёт из `GET /me`, поле `permissions`. Поля в ответе нет — открыто всё: панель,
которая правами не управляет, не должна получить пустое меню. Пустой список означает обратное —
не открыто ничего.

«Поля нет» и «ответ ещё не пришёл» при этом разные вещи: пока ответа нет, закрыто всё. Внутри
`PapiRouter` до этого не доходит — ответа там дожидается гард, — но `PermissionGate` панель
ставит и сама, вокруг кнопки или колонки, и там ждать некому. Открыться на время загрузки
значило бы показать закрытое каждому.

Набор прав принадлежит панели, поэтому перечисления в ядре нет: она объявляет свой enum у себя
(в скелете — `src/types/enums/permissions.enums.ts`) и вписывает его в `Papi.Permissions` —
одним файлом объявлений, как ключи каталога в `formatjs.d.ts`:

```ts
// src/types/permissions.d.ts
import type { Permission } from './enums/permissions.enums';

declare global {
  namespace Papi {
    interface Permissions {
      values: Permission;
    }
  }
}
```

После этого `PapiRoute.permission`, `permissions` в ответе `/me` и `PermissionGate` принимают
именно её enum, а не строку: `permission: 'view_uses'` не соберётся. Панель без объявления
получает `string` — как было.

Корень уводит на первый **доступный** раздел, а не просто на первый: раздел с `index` может
требовать права, которого у вошедшего нет, и вход тогда заканчивался бы отказом. Не доступно
ни одного — отказ и есть, с кнопкой выхода: возвращать такого человека в панель некуда, и
единственное, что ему остаётся, — войти кем-то другим.

Раздел можно объявить и прямо на корне — `{ path: '/' }`: своей ветки корню тогда не нужно, и
редиректа с него не будет.

Тем же правом панель закрывает что угодно у себя — `PermissionGate` из `@papi/routing`
принимает `permission`, `children` и необязательный `fallback` (по умолчанию `ForbiddenPage`).
Права россыпью отдаёт `usePermissions` из `@papi/hooks`: `permissions` и `hasPermission`.

Что сделать в панели: ничего, пока бэкенд не отдаёт `permissions`. Когда начнёт — расставить
`permission` в списке разделов.

### Ключом сообщения стал сам английский текст

Ключи были путями — `papi.login.submit`, `users.form.required`. Теперь ключ это сама английская
строка в нижнем регистре, а значение — её перевод:

```json
"sign in": "Войти",
"this field is required": "Обязательное поле",
"{count} users": "{count, plural, =0 {нет пользователей} one {# пользователь} other {# пользователей}}"
```

Плейсхолдеры едут внутри ключа как есть; ICU-формат остаётся в значении, поэтому совпадать с
ключом оно не обязано — см. `{count} users` выше и `"answered at {time}"` в каталоге панели.

Три следствия, ради которых это и делалось. Ключ читается в коде без похода в каталог. Ключ сам
себе запасной текст: ненайденную строку react-intl возвращает как id, и в интерфейс попадает
английский, а не `papi.login.submit`. Одинаковый английский схлопывается в один ключ — три
«Настройки» из меню, карточки пользователя и заголовка страницы стали одним `"settings"`.

**Длинные строки** ключом не становятся: больше одного предложения или длиннее полусотни
символов — и ключом идёт короткий ярлык в том же стиле, `"dates hint"`, `"signed out hint"`.
Иначе правка запятой в английском переименовывала бы ключ во всех каталогах сразу.

**Одинаковый английский в разных смыслах** разводится уточнением в скобках. У ядра такой случай
один: `"sign in"` — кнопка, `"sign in (page title)"` — заголовок формы; по-русски это «Войти» и
«Вход».

`PAPI_MESSAGES` вместе с `lib/constants/messages.constants.ts` удалён: `id` и `defaultMessage` в
нём стали одной и той же строкой. Ядро теперь зовёт `t('sign in')`, а ключи проверяет
`usePapiTranslation` — тот же приём, каким панель сужает свои ключи в `src/hooks/useTranslation`.
Там, где ключ едет данными до показа (`PapiApiError`, `extraOptions` эндпоинта), он заворачивается
в дескриптор через `papiMessage` из `@papi/i18n` — дескриптор остался, потому что рядом лежит
готовый текст от бэкенда, а ключ теперь и сам выглядит текстом.

Запасной текст `defaultMessage` заменён слоями в `I18nProvider`: под активным языком лежит
запасной — `en` у ядра, `I18nConfig.default` у панели. Побочный эффект — react-intl больше не
ругается на отставший перевод: ключ, найденный на запасном языке, для него ничем не отличается от
переведённого. Ругань в консоли теперь означает опечатку в ключе, а за полнотой каталогов нужно
следить их сверкой.

Ключи объявлены и самому react-intl — в `src/types/formatjs.d.ts`:

```ts
declare global {
  namespace FormatjsIntl {
    interface Message {
      ids: MessageKey;
    }
  }
}
```

`MessageDescriptor.id` в `@formatjs/intl` выводится из этого пустого глобального интерфейса, и
пока его не расширили, он равен `string`. Отсюда и разница, которая иначе выглядит необъяснимой:
`t('...')` подсказывает варианты, потому что сверяется с нашим union'ом, а `{ id: '...' }` — нет.
После объявления список ключей достаётся всем дескрипторам разом: `showSuccessMessage`,
`hideErrorMessage`, `labelId` у маршрута. Опечатка ловится на `tsc`, причём с подсказкой
«Did you mean».

Ядро читает результат через `MessageId` (`NonNullable<MessageDescriptor['id']>`) и без объявления
работает по-старому. Обратная сторона — с ним ядро ждёт, что `MessageKey` панели включает и его
ключи; перестанет включать — сломается сборка, а не интерфейс.

Что сделать в панели: переписать свои каталоги и все `t(...)` на новый стиль, завести
`types/formatjs.d.ts` по образцу выше. Ключ панели,
совпавший с ключом ядра, по-прежнему перекрывает его — так что `"sign out": "Выход"` у себя это
рабочий способ поменять формулировку ядра. Обратное тоже верно и стало вероятнее: ключ, случайно
совпавший с ядровым, теперь перекроет его молча.

### Переводы строк ядра приезжают вместе с ядром

Раньше переведён был только английский — он лежит в `defaultMessage` рядом с ключом, — а любой
другой язык панель перепечатывала у себя: два десятка ключей `papi.*` в своём каталоге. Копия
устаревала молча, и добавленная в ядре строка оставалась непереведённой до тех пор, пока её не
заметят в интерфейсе.

Теперь каталоги ядра лежат в `lib/i18n` (`en.json`, `ru.json`), и `I18nProvider` подмешивает их
по коду языка сам. Панель для этого ничего не подключает.

Каталог ядра идёт снизу, каталог панели — сверху, поэтому одноимённый ключ панели по-прежнему
перекрывает строку ядра: не нравится формулировка входа — пишется своя, и `lib/` трогать не
нужно. Языка, которого в `lib/i18n` нет, это не меняет: его строки ядра показываются
по-английски — раньше из `defaultMessage`, теперь нижним слоем каталогов, см. раздел выше.

Что сделать в панели: удалить ключи ядра из своих каталогов. Оставленные будут работать, но
они перекрывают ядро — то есть переписанная в ядре строка до такой панели не доедет, а каждый
новый ключ придётся по-прежнему дописывать руками.

### Гард проверяет сессию запросом `GET /me`

Токена в localStorage мало: он лежит там неделями и переживает и смену пароля, и удаление
пользователя. Поэтому перед каркасом `PapiRouter` спрашивает у бэкенда, кто вошёл, и ждёт
ответа — на каждой загрузке страницы, а не только сразу после входа.

Пока ответа нет, панель показывает `SplashScreen` — логотип на весь экран, в который наливается
цвет. Каркас в это время не рисуется намеренно: шапка с меню, мелькнувшая перед уходом на вход,
читается сбоем, а не загрузкой.

Логотип на нём — свой, если панель передала `logo` в `PapiRouter`: тот же проп уходит и в шапку
каркаса, и на экраны вне его — ожидание, ошибку гарда, отказ и 404. Не передан — логотип papi,
как и раньше.

Что происходит с ответом:

- пришёл — рисуется каркас, а имя, описание и аватар из ответа уходят в шапку;
- `401` — токен убирается, и панель уводит на `/login`, как и на любом другом запросе;
- другая ошибка (`500`, сеть, таймаут) — экран с «Повторить» и «Выйти». Токен при этом
  остаётся: лежать может сервер, а не сессия, и требовать из-за этого пароль незачем.

Ядро ждёт от ручки `{ id }` и необязательные `name`, `fullName`, `description`,
`avatarUrl` — всё, кроме `id`, `UserMenu` умеет не показывать. Оттуда же приезжают
`permissions`, которыми закрываются разделы, — см. раздел про право выше.

Что сделать в панели:

1. Завести на бэкенде `GET /me`. Без неё панель не откроется вовсе: `404` для гарда —
   такая же неудача, как `500`.
2. Убрать из пропа `user` у `PapiRouter` имя и аватар, если панель подставляла их сама:
   теперь их даёт ядро, а переданное встаёт поверх. Пункты меню остаются — их ядро не
   знает.
3. Панель, которая держала своего пользователя в слайсе или своём запросе, может забрать
   его из ядра: `useGetMeQuery` из `@papi/api` отдаёт тот же ответ из кеша, без второго
   запроса. Сбросить карточку после своей мутации — `invalidatesTags: [rtkTags.me]`.

### `projectId` переехал из сервисов в утилиты

Он читает адресную строку и хранилища, но React ему не нужен — по соглашению репозитория это
утилита, а не сервис. Файл теперь `lib/utils/projectId.util.ts`, и наружу всё выходит через
`@papi/utils`, а не `@papi/services`.

Суффикс `Service` в именах ушёл вместе с папкой:

| было                     | стало                |
| ------------------------ | -------------------- |
| `getProjectIdService`    | `getStoredProjectId` |
| `setProjectIdService`    | `setProjectId`       |
| `removeProjectIdService` | `removeProjectId`    |

`getProjectId` и `getProjectIdFromPath` не изменились — сменился только барель, из которого они
приезжают. Первая читает адрес, потом хранилище; вторая — только адрес.

Переименование, а не механическое снятие суффикса: `getProjectIdService` читает исключительно
хранилища, и имя `getProjectId` для неё было бы занято функцией с другим поведением.

### Роутер переехал в ядро

`BrowserRouter` теперь ставит сам `PapiProvider`. Свой роутер панели заводить не нужно —
и нельзя: react-router падает на роутере внутри роутера.

`basename` ядро берёт из `import.meta.env.BASE_URL`, то есть из `base` в `vite.config.ts`.
Панель, задеплоенная в подкаталог, настраивает его в одном месте, а не в двух.

Что сделать в панели: убрать `<BrowserRouter>` из `main.tsx` вместе с импортом — `<App />`
остаётся прямым потомком `<PapiProvider>`.

Нужен `HashRouter` или `MemoryRouter` — такая панель собирает цепочку у себя, из
`StoreProvider`, `I18nProvider`, `ThemeProvider` и `ApiProvider`: они экспортируются по
отдельности как раз для этого случая.

### Маршруты, вход и обработка ошибок переехали в ядро

`MainLayout` и `<Routes>` панель больше не собирает руками — их ставит `PapiRouter`. Вместе с
ними в ядро уехали экран входа, ненайденный адрес, редирект с корня и проверка токена.

Что появилось:

- `PapiRouter` — маршруты, каркас и гард. Без токена любой адрес ведёт на `/login`, а после
  входа человек возвращается туда, куда шёл.
- `LoginPage` и `NotFoundPage` в `@papi/pages`. Обе заменяются пропсами `loginElement` и
  `notFoundElement`.
- `useAuth` — `isAuthenticated`, `login`, `logout`. Выход убирает токен и сбрасывает кеш
  запросов.
- Ошибка любого запроса показывается через `message.error`. Текст берётся из поля `message`
  в теле ответа, а если его нет — из строк ядра. На конкретном эндпоинте показ убирается
  совсем — `extraOptions: { hideErrorMessage: true }` — или заменяется своей строкой:
  `{ hideErrorMessage: { id: 'could not create the user' } }`.
- Успех, наоборот, молчит, пока его не попросят: `extraOptions: { showSuccessMessage: true }` на
  мутации покажет `message.success` — текстом из поля `message` в ответе, а нет его,
  «Готово». Своя формулировка — дескриптором вместо `true`:
  `{ showSuccessMessage: { id: 'user created' } }`. На запросах
  проп не работает намеренно: ответ у них приходит и на перезапросах по фокусу окна.
- 401 убирает токен сам, откуда бы запрос ни ушёл.

Что сделать в панели:

1. Собрать разделы одним списком и отдать его `PapiRouter` вместо `MainLayout` с `<Routes>`
   внутри — путь раздела теперь пишется один раз, а не отдельно в меню и отдельно в маршруте.
2. Завести `src/constants/routes.constants.ts` с `{ ...papiRoutes, … }`, чтобы адреса лежали в
   одном месте.
3. Заменить самодельный выход на `useAuth().logout()`.
4. Проверить бэкенд: ядро ждёт `POST /auth/login` → `{ token }` и текст ошибки в поле
   `message`. Не сходится — панель отдаёт свою страницу входа через `loginElement`.
5. Переименовать свой слайс, если он звался `auth`: это имя занял слайс ядра, и чужой на нём
   будет пропущен с предупреждением в консоли.
6. Строки ядра переводить не нужно — переводы едут из `lib/i18n`, см. раздел выше. Ключ ядра
   в своём каталоге означает только одно: перекрыть формулировку ядра своей.

### Адрес API и сам api переехали в ядро

Ядро больше не принимает адрес бэкенда от панели: `configureApi`, `ApiConfig`, `setApiConfig`
и `getApiConfig` удалены, `baseApi` переименован в `api`. Адрес ядро читает само из
`VITE_API_BASE_URL`, а теги кеша объявляет тот файл эндпоинтов, которому они нужны.

Что сделать в панели:

1. Удалить `src/api/api.ts` — настраивать в нём больше нечего.
2. В файлах эндпоинтов брать api из ядра и там же объявлять теги:

   ```ts
   -import { api } from './api';
   +import { api } from '@papi/api';

   -export const usersApi = api.injectEndpoints({ … });
   +export const usersApi = api
   +  .enhanceEndpoints({ addTagTypes: ['User', 'Session'] })
   +  .injectEndpoints({ … });
   ```

   Тег, которого нет в `addTagTypes` этого файла, TypeScript в `providesTags` не пропустит —
   чтобы инвалидировать чужой, его нужно перечислить и здесь.

3. Убрать из `src/main.tsx` сайд-эффектный `import './api'`, если он там был.
4. Проверить, что `VITE_API_BASE_URL` есть в `.env`: без неё запросы уйдут на `/`, и ядро
   один раз предупредит об этом в консоли.
5. Убрать объявление `VITE_API_BASE_URL` из `src/vite-env.d.ts` — оно переехало в
   `lib/vite-env.d.ts` и теперь приезжает из ядра. Оставленное сборку не ломает: интерфейс
   общий, TypeScript сливает объявления, — но дублирует ядро.

## Чего нельзя делать

**Править `lib/`.** Ядро приходит из upstream. Любая правка там станет конфликтом при первом
же обновлении, а при неаккуратном разрешении — потеряется.

Нужно изменение в ядре — оно вносится в репозиторий papi и приезжает в панель через
`git merge upstream/main`. Пока изменения нет, обходной путь ищется на стороне панели: почти
всё в ядре настраивается пропсами и конфигом.

Запрет держит `.githooks/pre-commit` — он отклоняет коммит с изменениями под `lib/`, если
репозиторий опознан как панель: есть ремоут `upstream` либо `name` в `package.json` не `papi`.
Хук включается сам на `npm install` через скрипт `prepare`. Известное ограничение: при
установке с `--ignore-scripts` скрипт не отработает и хука не будет — тогда
`git config core.hooksPath .githooks` выполняется руками.

Обновлению ядра хук не мешает: пока идёт merge, cherry-pick или revert, он пропускает всё —
в индексе там лежит не правка панели, а то, что git переносит из чужого коммита.

Аварийный обход, если правка в `lib/` действительно нужна прямо сейчас:

```bash
PAPI_ALLOW_LIB=1 git commit …
```

**Импортировать вглубь ядра.** Панель видит только барели: `@papi/components`, `@papi/hooks`,
`@papi/store` и так далее. Глубокий путь вроде `@papi/components/layouts/MainLayout/MainLayout`
привязал бы её к расположению файлов внутри ядра — за этим следит eslint.

**Писать `useMemo` и `useCallback`.** Мемоизацию делает React Compiler: он включён в
`vite.config.ts` и расставляет кеш на сборке — в том числе держит стабильными ссылки на функции,
которые отдают хуки ядра. Импорт этих двух хуков из `react` отклоняет eslint. `React.memo` под
запрет не попадает: он про рендер компонента, а не про мемоизацию значений.

## Что где лежит

| Путь                                                                        | Владелец      | При `git merge upstream/main`            |
| --------------------------------------------------------------------------- | ------------- | ---------------------------------------- |
| `lib/**`                                                                    | ядро          | Обновляется, конфликтов не бывает        |
| `.claude/`, `.githooks/`, `.github/`                                        | ядро          | Обновляется                              |
| `tsconfig.json`, `vite.config.ts`, `eslint.config.js`, `prettier.config.js` | ядро          | Обновляется; правки панели дают конфликт |
| `package.json`                                                              | ядро и панель | Конфликт возможен                        |
| `src/**`                                                                    | панель        | Ядро трогает только скелет — см. выше    |
| `index.html`, `public/`, `README.md`, `.env*`                               | панель        | Ядро трогает крайне редко                |

Имя и аббревиатура панели — `VITE_APP_NAME` и `VITE_APP_ABBR` в `.env`, см. «Создать панель».

Конфиги принадлежат ядру ради одинаковости панелей. Всё настраиваемое поэтому вынесено в
переменные окружения — типовой панели корневые конфиги править не нужно.

Переменные объявлены там же, где их читают: свои панель описывает в `src/vite-env.d.ts`,
переменные ядра лежат в `lib/vite-env.d.ts`. Интерфейс `ImportMetaEnv` общий — TypeScript
сливает объявления, — а значение по умолчанию в обоих случаях идёт в `.env.example`.

Адрес бэкенда — переменная ядра: `VITE_API_BASE_URL` читает `lib/services`, и панель его
никуда не передаёт. Своего api она тоже не создаёт — берёт готовый из `@papi/api` и
дописывает в него эндпоинты у себя в `src/api`:

```ts
// src/constants/tags.constants.ts — один раз на всю панель
export const rtkTags = injectTags({ user: 'User', order: 'Order' });

// src/api/users.api.ts — и дальше только эндпоинты
export const usersApi = api.injectEndpoints({ endpoints: (build) => ({ … }) });
```

## Команды

| Команда                | Что делает                                                   |
| ---------------------- | ------------------------------------------------------------ |
| `npm start`            | Дев-сервер с моком бэкенда, по сети и с открытием в браузере |
| `npm run dev`          | Он же на 5173, но без мока и без браузера                    |
| `npm run build`        | Тайпчек и сборка в `dist/`                                   |
| `npm run preview`      | Локальный показ собранного                                   |
| `npm run typecheck`    | `tsc --noEmit`                                               |
| `npm run lint`         | eslint                                                       |
| `npm run lint:fix`     | eslint --fix и prettier                                      |
| `npm run format:check` | Проверка форматирования                                      |

`npm start` ждёт мок по пути `tmp/vite.config.mock.ts`. Папки нет в репозитории — у каждой
панели свой мок, — поэтому в свежем клоне команда падает, пока его туда не положат. До этого
момента панель поднимается через `npm run dev`, и запросы уходят по адресу из `.env`.
