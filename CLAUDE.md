# papi

Базовый проект админ-панелей: ядро в `lib/`, панель в `src/`. Панели — клоны этого
репозитория, ядро приезжает к ним через `git merge upstream/main`.

## Язык ответов

Отвечай пользователю **по-русски**.

Это правило только про ответы в чате. Стиль кода оно не меняет: комментарии, названия и
тексты в самих файлах пишутся так же, как в существующих, — новый язык туда не переносится.

## `lib/` — read-only в панелях

Пойми, где ты, прежде чем править ядро. Признака два, и хватает любого:

- есть ремоут `upstream` **или** `name` в `package.json` не равен `papi` — это панель.
  **`lib/` не трогаем.** Правка там станет конфликтом при первом же обновлении ядра. Нужное
  изменение вносится в репозиторий papi. Пока его нет, решение ищется на стороне панели: почти
  всё в ядре настраивается пропсами и конфигом.
- ремоута `upstream` нет и `name` — `papi` — это сам papi. Ядро здесь и правится.

Двух признаков, а не одного: ремоуты лежат в `.git/config` и при клонировании не переносятся,
поэтому у второго разработчика панели `upstream` не будет, а имя пакета закоммичено и
переживает клон.

`.githooks/pre-commit` отклонит коммит с изменениями под `lib/` в панели. Обходить его через
`PAPI_ALLOW_LIB=1` без явной просьбы пользователя нельзя.

## Границы импортов

- Панель видит ядро только через барели: `@papi/components`, `@papi/hooks`, `@papi/store`.
  Глубокие пути (`@papi/components/layouts/MainLayout/MainLayout`) запрещены — eslint ругается.
- Внутри `lib/` импорты относительные. Алиас `@papi/*` там не используется.
- Ядро не зависит от панели: импортировать что-либо из `src/` в `lib/` нельзя ни при каких
  обстоятельствах.

Новая публичная сущность ядра добавляется в барель своей папки (`lib/<папка>/index.ts`) —
больше нигде её регистрировать не нужно, алиас и резолв работают на папку целиком.

## Мемоизация — только автоматическая

**`useMemo` и `useCallback` не используются.** Ни в `lib/`, ни в `src/`, ни «по необходимости»,
ни для колбэков, которые хук отдаёт наружу. Значение считается прямо в теле, колбэк объявляется
обычной функцией.

Мемоизацию делает React Compiler — он включён в `vite.config.ts` и на сборке расставляет кеш сам,
включая стабильные ссылки на функции из хуков. Написанное руками он не улучшает, а дублирует.

Импорт `useCallback` или `useMemo` из `react` отклоняет eslint, так что нарушение видно на
`npm run lint`, а не на ревью.

`React.memo` под правило не попадает — это про рендер компонента, а не про мемоизацию значений.

## Проверка работы

```bash
npm run typecheck && npm run lint && npm run build
```

Сборки у ядра нет — `lib/` компилируется вместе с `src/`, поэтому отдельного шага для правки
ядра не существует, и dev-сервер подхватывает её сразу.
