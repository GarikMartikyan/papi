# api-endpoint-pattern — как papi ходит на бэкенд

Главное правило этого скилла одно: **бэкенд вернул изменённую сущность — она кладётся в кеш,
а не выбрасывает его.** Инвалидация тега здесь не режим по умолчанию, а исключение с
объяснением. Всё остальное ниже — обвязка вокруг этого.

## Один api на всю панель

`createApi` живёт в ядре (`lib/api/api.ts`). Панель зовёт на нём `injectEndpoints`:

```ts
import { api } from '@papi/api';

export const usersApi = api.injectEndpoints({
  endpoints: (build) => ({ … }),
});
```

Свой `createApi` панель не заводит **никогда**. Редьюсер и middleware у api регистрируются в
момент создания стора, а стор создаёт ядро — второй api к уже созданному не подключить, и его
запросы просто не поедут.

## Файл на ресурс

Панель кладёт файлы прямо в `src/api/<resource>.api.ts`, ядро — в
`lib/api/endpoints/<resource>.api.ts`. Подпапка нужна тому, у кого рядом лежит ещё и устройство
самого api.

Внутри файла порядок фиксированный: **сначала запросы, потом мутации** — сначала то, что читает,
потом то, что меняет прочитанное. Тот же порядок, в каком они стоят и в теле компонента.

Оба типа-параметра указываются всегда: `build.query<Result, Arg>`, `build.mutation<Result, Arg>`.
Ручке ничего не передают — вторым идёт `void`: пропустить его нельзя, tsc валит такую ручку на
TS2558, а `void` говорит прямо, что аргумента нет.

Адрес ресурса — константой на уровне модуля (`const USERS_PATH = '/users'`), чтобы он не
переписывался в каждой ручке.

Хуки панель отдаёт одной деструктуризацией — это просто список того, что файл отдаёт наружу:

```ts
export const { useGetUsersQuery, useCreateUserMutation } = usersApi;
```

Ядро — по одному (`export const useGetMeQuery = meApi.useGetMeQuery;`): каждый его хук публичен
для всех панелей, и каждому нужно своё описание над ним.

## Сущности приходят из `types/`, в ручке — только производные

Интерфейс сущности объявляется в папке типов своего слоя — панель кладёт его в
`src/types/interfaces/<resource>.interfaces.ts`, ядро в
`lib/types/interfaces/<resource>.interface.ts`, — а файл ручек его импортирует:

```ts
import type { User } from '../types/interfaces/user.interfaces';
```

`interface` в `*.api.ts` не объявляется **никогда**, даже когда сущность нужна пока одной ручке.
Одной она не остаётся: её показывает таблица, её правит форма, её принимает хук. Объявленная
рядом с ручками, она превращает файл ручек в модуль типов, и следующий, кому нужен `User`, берёт
его из `users.api.ts` — компонент оказывается привязан не к сущности, а к тому месту, откуда
данные однажды пришли.

В самом файле остаётся то, что выводится из уже объявленного, — утилитные типы:

```ts
createUser: build.mutation<User, Omit<User, 'id'>>({ … }),
updateUser: build.mutation<User, Pick<User, 'id'> & Partial<Omit<User, 'id'>>>({ … }),
```

`Omit`, `Pick`, `Partial`, `Required`, объединение уже описанных — можно: они ничего не заводят,
а сужают то, что уже названо в `types/`. Поле, добавленное в сущность, доезжает до пейлоада само;
переписанный руками пейлоад разошёлся бы с ней молча.

Производная, которой нужно имя — потому что её ждёт ещё и форма, хук или пропсы, — переезжает в
`src/types/types/<resource>.types.ts` и импортируется оттуда:

```ts
export type CreateUserPayload = Omit<User, 'id'>;
```

Граница простая: **описать** сущность — в `types/`; **сузить** уже описанную — можно по месту.

## Тег объявляется один раз

Тег — это строка, связывающая два места, и опечатка в ней ничего не ломает на сборке: она просто
тихо перестаёт работать. Поэтому строкой по месту тег не пишется никогда.

Панель объявляет свои теги одним вызовом в `src/constants/tags.constants.ts`:

```ts
export const rtkTags = injectTags({ user: 'User' });
```

и один раз описывает их в `src/types/tags.d.ts` (`Papi.ApiTags`). Без этого объявления `PapiTag`
схлопывается в `string`, сборка остаётся целой, а `providesTags` перестаёт что-либо проверять.
`injectTags` возвращает и теги ядра, так что `@papi/constants` ради `rtkTags.me` не нужен.

Сам файл ручек тег не объявляет — импортирует: панель `rtkTags` из
`src/constants/tags.constants.ts`, ядро `papiRtkTags` из `lib/constants/tags.constants.ts`.
Локальный `{ user: 'User' }` рядом с ручками работает ровно до первого расхождения: в `tagTypes`
попадает только то, что прошло через `injectTags`, и тег, переименованный в `tags.constants.ts`,
оставит вторую копию строки на месте — сборка цела, инвалидация молча перестала работать.

`providesTags` ставится у запроса **всегда**, даже когда никто его не инвалидирует. Он стоит одну
строку и оставляет открытыми оба пути: сбросить кеш руками (`api.util.invalidateTags`) и
откатиться к инвалидации там, где патч не справился.

## Тосты — через `extraOptions`

| нужно | как |
|---|---|
| обычная ошибка тостом | ничего не писать — так по умолчанию |
| ошибку показывает сама страница | `hideErrorMessage: true` |
| своя формулировка вместо ответа бэкенда | `hideErrorMessage: papiMessage('…')` или `{ id: '…' }` |
| подтвердить удачную мутацию | `showSuccessMessage: true` — текст из ответа |
| своя формулировка подтверждения | `showSuccessMessage: { id: 'user created' }` |

Умолчания разные не случайно: ошибку человек не ждёт — она приходит вместо результата, — а успех
он и так видит по экрану. Успех показывается только на мутациях.

`papiMessage` сверяет ключ с каталогом ядра, поэтому для своей строки панель пишет дескриптор
литералом: `{ id: 'user created' }`. Ключ из каталога панели `papiMessage` не пропустит.

Литерал при этом не остаётся непроверенным: `src/types/formatjs.d.ts` подставляет каталог панели
в `FormatjsIntl`, и дескриптор с ключом, которого нет в `src/i18n/*.json`, валится на TS2820 —
`Type '"order created"' is not assignable to type 'MessageKey'`. Строка заводится в каталоге, а
не подгоняется под то, что уже есть.

## Кеш обновляется ответом, а не инвалидацией

Бэкенд на создание и на изменение отвечает изменённой записью. Значит, к моменту, когда мутация
завершилась, новые данные **уже в руках**, и `invalidatesTags` тратил бы второй круг по сети на
то, чтобы получить их ещё раз: лишний RTT, `isFetching` на таблице, которую человек в этот момент
читает, и список, отстающий от собственного действия на скорость сети.

Поэтому мутация правит кеш сама:

```ts
onQueryStarted: async (_payload, { dispatch, queryFulfilled }) => {
  try {
    const { data: created } = await queryFulfilled;

    dispatch(
      usersApi.util.updateQueryData('getUsers', undefined, (users) => {
        users.push(created);
      }),
    );
  } catch {
    /* Кеш не трогаем — в нём по-прежнему правда. Тост показал `papiBaseQuery`. */
  }
},
```

Что здесь важно и почему:

- **Диспатч идёт через `usersApi`, а не через `api` из `@papi/api`.** У api ядра
  `endpoints: () => ({})`, его тип про `getUsers` не знает, и имя запроса не пройдёт:
  `'getUsers' is not assignable to parameter of type 'never'`. Ссылка на `usersApi` изнутри его
  же объявления работает — `onQueryStarted` вызывается по мутации, задолго после загрузки модуля.
- **Второй аргумент — аргумент запроса, он же ключ кеша.** У `getUsers` аргумента нет, поэтому
  `undefined`. У запроса с фильтрами передаются ровно те же фильтры — иначе патч уедет в чужую
  запись кеша и не сделает ничего.
- **Патч по незаполненному кешу — не ошибка.** RTK Query видит запись со статусом
  `uninitialized` и выходит. Проверять, открыт ли сейчас список, не нужно.
- **`try`/`catch` обязателен.** Сам `queryFulfilled` RTK Query гасит от unhandled rejection, а
  промис, который возвращает `onQueryStarted`, — нет: `await` без `catch` даст в консоли
  необработанный reject на каждой неудачной мутации. В `catch` при этом делать нечего — тост уже
  показал `papiBaseQuery`, а кеш не менялся.
- **`updateQueryData` правит то, что в кеше есть; `upsertQueryData` заводит запись.** Список
  патчится первым, карточка (`getUser`) — вторым, через upsert: её могли ни разу не открыть.
  Upsert возвращает промис, поэтому пишется с `void`.

### Запрос с аргументом — ключей в кеше несколько

Аргумент запроса и есть ключ его кеша, поэтому у запроса с фильтрами в кеше живёт по записи на
каждый набор, с которым его звали. Патч по одному «главному» набору прошёл бы мимо остальных, и
вкладка с другим фильтром показывала бы старое. Ключи спрашиваются у самого RTK Query:

```ts
for (const filters of ordersApi.util.selectCachedArgsForQuery(lifecycle.getState(), 'getOrders')) {
  dispatch(
    ordersApi.util.updateQueryData('getOrders', filters, (orders) => { … }),
  );
}
```

`getState` при этом не разбирается деструктуризацией, в отличие от `dispatch`: в типах RTK Query
это метод, и оторванный от своего объекта он поднимает `unbound-method` у eslint. Поэтому весь
контекст берётся параметром (`lifecycle`), а из него достаётся только то, что объявлено функцией.

Патч по всем ключам верен, пока правка не меняет попадание записи в фильтр. Меняет — заказ
остался бы в выборке, которой больше не соответствует, и правильной становится инвалидация.

Что делает мутация — по типу:

| мутация | что с кешем |
|---|---|
| создание | `push` ответа в список + `upsertQueryData` карточки |
| изменение | замена по `id` целиком (не слияние с пейлоадом) + upsert карточки |
| удаление | `splice` по `id` **из аргумента** — ответа у удаления обычно нет |

Замена целиком, а не слияние с тем, что отправляли: в ответе лежат и поля, которые бэкенд
посчитал сам, — `updatedAt`, версия, вычисленный статус.

## Когда инвалидация всё-таки правильная

`invalidatesTags` остаётся рабочим инструментом ровно там, где собрать новое состояние из ответа
нечем:

- ответ не содержит сущности — `204`, массовые операции, импорт;
- сервер считает поверх записи: агрегаты, счётчики, права, порядок в списке;
- список сортируется и пагинируется на сервере — место новой записи локально неизвестно;
- мутация задевает чужие ресурсы, и их запросы патчить пришлось бы по одному;
- мутация меняет то, по чему список фильтруется или сортируется, — запись осталась бы в чужой
  выборке;
- вариантов аргумента у запроса столько, что обход всех ключей выходит дороже перезапроса.

В этих случаях инвалидация пишется **с комментарием, почему патча не хватило**. Без комментария
она читается как выбор по инерции, и следующий, кто откроет файл, не поймёт, оставить её или
заменить.

## Оптимистичное обновление — отдельная просьба

Патч **до** ответа (с `patchResult.undo()` в `catch`) по умолчанию не пишется. Он показывает
человеку то, чего на сервере ещё нет, и на неудаче экран дёргается обратно. Заводится он там, где
задержка заметна на каждом действии — переключатель в списке, перетаскивание порядка, — и только
когда об этом попросили.

## Именование

| что | как |
|---|---|
| файл | `<resource>.api.ts` — `users.api.ts` |
| api ресурса | `<resource>Api` — `usersApi` |
| запрос списка / записи | `getUsers`, `getUser` |
| мутации | `createUser`, `updateUser`, `deleteUser` |
| путь ресурса | `USERS_PATH` на уровне модуля |

## Пример целиком

`example/users.api.ts` — запросы, все три мутации с патчем кеша и одна ручка, которой инвалидация
подходит больше. Он лежит в `tsconfig.json` и линтуется вместе с проектом, поэтому показанное в
нём компилируется.

Разбор сущностей по папкам типов — скилл `component-pattern` (раздел про типы), логика поверх
запросов — `hook-pattern`.
