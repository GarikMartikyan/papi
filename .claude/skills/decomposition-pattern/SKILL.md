# decomposition-pattern — как papi разбирает компонент на части

Правило «один файл — один компонент» из скилла `component-pattern` отвечает на вопрос
«сколько компонентов в файле». Этот скилл — про то, когда компонентов становится больше
одного и куда девать новые.

## Когда пора

Достаточно одного признака:

- **компонент не читается с одного экрана** — приходится скроллить, чтобы понять, что он
  рисует;
- **JSX глубже четырёх уровней вложенности** — дальше разметка перестаёт держаться в голове,
  и закрывающий тег уже не найти глазами;
- **больше ~10 хуков** — компонент занят несколькими делами сразу;
- **два несвязанных куска состояния** — одно меняется, второе к этому не имеет отношения;
- **кусок JSX встречается второй раз** — здесь и на соседнем экране;
- **у куска разметки есть собственное состояние** — открыт/закрыт, наведение, черновик формы.
  Оно тянет за собой перерисовку всего родителя, а нужно одному блоку.

## Когда не пора

Декомпозиция — не самоцель, и файл на 200 строк сам по себе не диагноз.

- **Ради короткого файла.** Компонент, который читается сверху вниз и делает одно дело,
  разбивать незачем: три файла по 60 строк читаются хуже одного на 180, потому что между
  ними нужно прыгать.
- **Часть, у которой все пропсы — из родителя.** Восемь пропсов и ни одного собственного
  решения означают, что граница проведена не там: вынесли разметку, а не ответственность.
  Либо граница переносится, либо кусок возвращается на место.
- **Обёртка вокруг двух строк.** `<div>` с заголовком отдельным компонентом не становится.

## Куда кладётся часть

Часть живёт в папке `elements/` внутри папки своего владельца:

```
lib/components/layouts/MainLayout/
  MainLayout.tsx            ← владелец, в барели
  elements/
    MainLayoutHeader.tsx    ← части, наружу не выходят
    MainLayoutNav.tsx
    MainLayoutSider.tsx
    MainLayoutTrigger.tsx
```

Компонент лежал плоским файлом (`shared/UserMenu.tsx`) и обзавёлся частями — он превращается
в папку: `shared/UserMenu/UserMenu.tsx` и `shared/UserMenu/elements/`. Папка заводится в тот
момент, когда появляется первая часть, а не заранее: вокруг одного файла она добавляла бы
уровень, ничего не разделяя.

Часть общая у двух владельцев — она больше не часть. Такой компонент переезжает в `shared/`
(в ядре) или в `src/components/` (в панели) и становится самостоятельным, со своим публичным
интерфейсом.

## Как называется

Имя части начинается с имени владельца: `MainLayoutHeader`, `MainLayoutTrigger`. Слово из
середины можно опустить, если владелец узнаётся и без него — `AuthLayout` → `AuthBackground`.

Смысл в том, чтобы часть нельзя было спутать с самостоятельным компонентом: `Header.tsx`
рядом с `Sider.tsx` выглядит как готовый к переиспользованию набор, а он существует ровно
ради одного родителя.

Файл называется по компоненту, как везде: один файл — один компонент — одно имя.

## Часть берёт состояние пропсами

Часть не ходит в стор и не делает свой запрос за тем, чем уже владеет родитель. Состояние
приходит пропсами, а обратная связь — колбэками:

```tsx
export interface MainLayoutTriggerProps {
  collapsed: boolean;
  onToggle: () => void;
}
```

Причина не в чистоте, а в переиспользовании. Кнопка сворачивания в `MainLayout` управляет
двумя колонками: левая хранится в `config`-слайсе, правая — в локальном стейте родителя.
Часть, которая сама читала бы селектор, умела бы сворачивать только первую.

Своё за данными часть идёт только тогда, когда родителю они не нужны вовсе — иначе один и
тот же запрос живёт в двух местах и расходится.

## Пропсы части — плоский интерфейс

Публичная обёртка вокруг antd наследует пропсы базы (`extends SelectProps`) — см.
`component-pattern`. Часть так не делает: она не обёртка, а кусок родителя, и её интерфейс
перечисляет ровно то, что родитель передаёт. Ни `...rest` в базу, ни `style` наружу — если
части понадобилось и то и другое, она уже самостоятельный компонент, и ей место в `shared/`.

Тип, общий у части и владельца, объявляется у владельца, а часть импортирует его через
`import type`. Такой импорт стирается на сборке, поэтому встречный импорт самой части цикла
не создаёт.

## В барель часть не попадает

`lib/components/index.ts` перечисляет только владельцев. Часть в барели означала бы, что
панель может собрать каркас из кусков, — а тогда любое их перемещение станет ломающим
изменением для всех панелей.

Панели часть не нужна: она получает `MainLayout` целиком и настраивает его пропсами.

## Логика уходит в хук, а не в ещё один компонент

Компонент разросся не разметкой, а логикой — декомпозиция ему не поможет: вынесенная часть
получит десяток пропсов и вернёт десяток колбэков. Такое уходит в хук (`useX.ts`) — см.
скилл `hook-pattern`. Компонент остаётся один, а читать его становится нечего: вызов хука и
разметка.

## Ядро и панель

Декомпозиция компонента ядра делается в репозитории papi, а не в панели: `lib/` в панелях
read-only, и перестановка файлов там станет конфликтом при первом же `git merge upstream/main`.
Панель разбирает только своё — `src/pages/<Page>/elements/`, `src/components/`.
